`../core/localization.md` is authoritative. This skill adapts it to client/UI implementation.

## Localization abstraction
All user-facing client UI text must resolve through the project's localization system. The implementation may be i18next, Unity String Tables, native string catalogs or another suitable platform solution.

Do not hardcode user-facing labels, alerts, validation messages or empty-state copy in application code when they belong to the product localization catalog.

## Bundled availability
The client must bundle enough English localization to boot and remain basically usable without network access.

Every production-supported locale should also be bundled when the product's distribution model reasonably permits it. Remote packs/overrides may update copy, but a network call must not be required to render the core UI.

## Keys
Use semantic keys from the English canonical contract. Reuse an existing semantically equivalent key before creating another.

Do not enforce exactly two dotted levels; use enough namespace/context to avoid ambiguity.

## Resolution
Default order:
1. persisted explicit user choice;
2. best supported device locale/language;
3. English.

Do not change explicit UI language merely because country, currency or timezone changes.

## Dynamic messages
Use named parameters and the localization engine's plural/select/message facilities. Avoid sentence-fragment concatenation and English-only singular/plural branches.

## Formatting
Use locale-aware platform formatting for number/date/time/unit presentation. Currency code/value comes from product/business data; locale affects presentation.

## Error codes
When an API returns stable machine-readable error codes, map them to frontend localization keys. Do not display or branch on backend human-language text unless that text is intentionally server-rendered content.

## Validation
Before release, verify English completeness, supported locale completeness, placeholder compatibility and representative long-string/plural/fallback behavior.

## Checklist
- [ ] Core localization standard followed
- [ ] English client fallback is bundled and complete
- [ ] No hardcoded user-facing UI copy
- [ ] Existing semantic keys reused
- [ ] Explicit language choice outranks device locale
- [ ] Dynamic grammar uses localization features
- [ ] Formatting is locale-aware
